  1. Models & API, as I read them

  JobStatus is an append-only event log, not a mutable field. The prompt's PATCH
  wording — "creating a new JobStatus entry" — makes that explicit.
  Job.current_status is therefore a projection of that log. Everything else
  follows from that framing.

  - Job: id, name, created_at, updated_at + denormalized current_status,
  current_status_at
  - JobStatus: id, job (FK CASCADE), status_type (4 TextChoices), timestamp
  - GET /api/jobs/ cursor-paginated with current_status inline · POST creates
  job + initial PENDING in one transaction · PATCH appends an event (also
  handles rename) · DELETE cascades · plus GET /api/health/ so make test can
  wait for readiness instead of racing Postgres

  2. Slices

  11 vertical slices, each with one scoped Playwright spec. Slices 0–4 (health →
  list → create → patch → delete) are backend-only but still tested through
  Playwright's request fixture — same runner, same make test, no second
  framework. Slices 5–10 layer the UI on: list → create form → status update 
  (the prompt's required critical flow) → delete → fault-injected error handling
  → pagination at scale. Slice 11 is README + a clean-machine make test rerun.
  Details in docs/PLAN.md.

  3. On your two questions — I agree, with one refinement each

  Millions of jobs: your reading is right, and I'd state it in the README as an
  explicit assumption: the dataset is large, a single user's viewport is not.
  The real job is making every query cost proportional to the page, not the
  table. Concretely that means cursor over offset pagination — OFFSET 500000
  makes Postgres walk and discard half a million rows, and DRF's page-number
  paginator additionally fires a COUNT(*) on every request, which is a full
  index scan per page load. Keyset pagination has neither problem.

  Current status: agreed on denormalizing onto Job — the deciding factor is
  ?status=RUNNING, which a derive-on-read subquery cannot serve without
  computing the latest status for every job in the table. One refinement:
  compare the incoming event against current_status_at, not updated_at.
  updated_at bumps on every save, so a rename would make a subsequent legitimate
  status event look stale and get silently dropped.

  4. Things the prompt leaves open

  Flagging the ones that don't need a decision from you — I'll note them in the
  README rather than build for them: no auth/multi-tenancy (the prompt never
  mentions users, so one shared job list); no state-machine constraints (prompt
  says update to any defined state, so COMPLETED → RUNNING is allowed); repeat 
  PATCH of the same status still appends an event, since it's a log of
  observations, not a diff.

  DockerHub access, but the standard Playwright image lives on
  mcr.microsoft.com, not DockerHub. I'll build the e2e image from
  node:22-bookworm instead. Getting that wrong fails make test on their machine,
  which per the prompt ends the evaluation.

     Decisions settled with the user

     - JobStatus is an append-only event log; Job.current_status is a
     denormalized projection of it.
     Justified by ?status=RUNNING — a derive-on-read subquery must compute the
     latest status for every row
     in the table before it can filter, which cannot use an index.
     - Guard the projection on current_status_at, not updated_at — updated_at
     moves on every save, so
     a rename would make a later legitimate status event look stale and get
     silently dropped.
     - Server-stamped timestamps. The guard still ships (one comparison, makes
     writes idempotent under
     replay) but is inert today.
     - Status history exposed: GET /api/jobs/<id>/statuses/ + an expandable
     per-row timeline. Lets tests
     assert the log is genuinely append-only and that DELETE cascaded.
     - nginx serves the static Vite build and reverse-proxies /api → no CORS, no
     build-time API URL.
     - make test = Playwright only (exactly what the prompt specifies); make 
     test-backend /
     make test-all run pytest-django separately, so an unrelated unit test can
     never fail the gate.
     - Out of scope, documented in the README rather than built: no
     auth/multi-tenancy, no status state machine
     (any transition allowed), repeat PATCH of the same status still appends an
     event.

     Core implementation notes

     services.record_status(job, status_type) is the only function that writes
     current_status. It runs in
     transaction.atomic() with select_for_update() on the job row, appends the
     JobStatus, then applies the
     projection per the guard. POST and PATCH both route through it, so exactly
     one code path can create
     drift between log and projection.

     Indexes — JobStatus(job_id, timestamp DESC, id DESC), Job(created_at DESC, 
     id DESC),
     Job(current_status, created_at DESC, id DESC). id DESC as tiebreaker
     everywhere so ordering is total;
     without it, rows sharing a timestamp can be skipped or repeated across
     keyset pages.

     Pagination — DRF CursorPagination, ordering = ("-created_at", "-id"), page
     size 25. No COUNT(*)
     on the hot path.

     Validation tiers

     Three tiers, so the inner loop stays fast and the expensive gate still runs
     often enough to catch drift.

     Tier: T1 — lightweight
     Command: make test-spec SPEC=03-update-job-api (one spec against the
     already-running stack, no rebuild) · make test-backend during backend
     slices
     Cost: seconds
     When: after every meaningful change, inside a slice
     ────────────────────────────────────────
     Tier: T2 — suite
     Command: make test (rebuild + full Playwright suite, stack already
     provisioned)
     Cost: ~1–2 min
     When: at the close of every slice — this is what catches cross-slice
     regressions
     ────────────────────────────────────────
     Tier: T3 — cold gate
     Command: make clean && make build && make test from a pruned Docker +
     --platform linux/amd64 build check
     Cost: several min
     When: slices 0, 4, 7, 11 only

     T3 is deliberately rare — it's the evaluator's exact path, and it's slow.
     It runs at slice 0 (proves the
     gate before any features exist), slice 4 (backend complete), slice 7
     (required critical flow green), and
     slice 11 (final). Any slice that touches Docker, compose, the Makefile, or
     a dependency also triggers
     T3, regardless of position — that's the class of change that breaks cold
     builds while passing warm ones.
